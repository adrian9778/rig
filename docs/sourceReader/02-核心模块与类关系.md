## 🔧 泛型客户端架构（0.42 后重构的核心）

### `Provider` trait：一个 provider 值类型

```rust
// File: crates/rig-core/src/client/mod.rs:246

pub trait Provider: Clone + Debug + WasmCompatSend + WasmCompatSync + 'static {
    const NAME: &'static str;          // 如 "openai"
    const BASE_URL: &'static str;      // 默认 base URL
    const VERIFY_PATH: &'static str;   // VerifyClient 校验凭据用的端点

    type ApiKey: ApiKey;      // BearerAuth / Nothing / provider 专属 key 类型
    type Config: Default + Clone;   // builder 设置，`()` 表示无
    type EnvInput;            // from_val 的入参

    fn build(config: Self::Config, api_key: &Self::ApiKey) -> http_client::Result<Self>;
    fn finish<H>(&self, builder: ClientBuilder<Self, H>) -> http_client::Result<ClientBuilder<Self, H>> { Ok(builder) }  // 默认恒等
    fn from_env<H: HttpClientExt>(http: H) -> ProviderClientResult<Client<Self, H>>;
    fn from_val<H: HttpClientExt>(input: Self::EnvInput, http: H) -> ProviderClientResult<Client<Self, H>>;
    fn build_uri(&self, base_url: &str, path: &str) -> String { /* 默认单斜杠拼接；query-string 鉴权的 provider 在此追加 key */ }
    fn prepare(&self, req: http_client::Builder) -> http_client::Result<http_client::Builder> { Ok(req) }  // 每请求定制
}
```

### `Has*` 能力 trait：一种能力 = 一个实现

`HasCompletion`、`HasEmbeddings`、`HasRerank`、`HasTranscription`、`HasModelListing`、`HasImageGeneration`（feature `image`）、`HasAudioGeneration`（feature `audio`）。每个只做一件事：命名具体模型类型并从 client 构造它。

```rust
// File: crates/rig-core/src/client/completion.rs（HasCompletion 形态）

impl HasCompletion for Example {
    type Model<H> = ExampleModel<H> where H: ModelTransport;
    fn completion_model<H: ModelTransport>(client: &Client<Self, H>, model: String) -> ExampleModel<H> { ... }
}
```

本模块的 blanket impl 把它们变成用户面上的 `CompletionClient` / `EmbeddingsClient` / `RerankingClient` / `TranscriptionClient` / `ModelListingClient` / `VerifyClient` trait——所以 `client.completion_model("gpt-5.2")` 直接返回该 provider 自己的模型类型。**provider 缺哪种能力 = 它没实现那个 trait**，缺方法由编译器报告。

### `Client<P, H>` 与 builder 状态机

```rust
// File: crates/rig-core/src/client/mod.rs:342

pub struct Client<P, H = BoxedHttpClient> {
    base_url: Arc<str>,
    headers: Arc<HeaderMap>,
    http_client: H,      // 任意 HttpClientExt；rig-core 不选具体传输
    provider: P,
}

pub struct ClientBuilder<P: Provider, H = Missing> {
    base_url: String,
    api_key: Option<P::ApiKey>,
    headers: HeaderMap,
    http_client: H,      // Missing = 尚未选择传输
    config: P::Config,
}
```

- `builder()` 定义在 `Client<P, Missing>` 上，`H` 自动推断为 `Missing`，所以 `provider::Client::builder()` 不需要标注。
- `http_client(h)` 把 `H` 槽从 `Missing` 推进到具体传输；rig-core 自己的 `build()` 只在 `H: HttpClientExt` 时可用。
- **rig-reqwest 的 `DefaultTransportBuilder`** 提供"无传输 build"：给 `Missing` 状态的 builder 默认填一个 `ReqwestClient`，这就是 `Client::new(key)` / `Client::from_env()` / `builder().…build()` 这些一步到位构造的来源（经门面 prelude 重导出）。
- `Client::boxed()` 把传输擦除成 `BoxedHttpClient`，供 host 用一个传输挂多家 provider。
- `ApiKey` trait：`into_header()` 决定是否注入默认 Authorization 头；`absent()` 决定"无凭据"是否合法（`Nothing` 合法，`BearerAuth` 不合法——`build` 报 `MissingApiKey`）。`BearerAuth` 的 Debug 输出 `BearerAuth(<redacted>)`，`Client` 的 Debug 过滤 `Authorization`/`api-key` 头。

### provider 模块的别名模式

每个 provider 模块导出（以 openai 为例，`crates/rig-core/src/providers/openai/client.rs:46`）：

```rust
pub type Client<H = crate::http_client::BoxedHttpClient> = client::Client<OpenAIResponses, H>;
pub type ClientBuilder<H = crate::markers::Missing> = client::ClientBuilder<OpenAIResponses, H>;
```

### Agent 构造与共享配置

`AgentBuilder`（`agent/builder.rs:143`）持有 `config: AgentConfig` + `tool_state`（`NoToolConfig`/`WithBuilderTools` 类型状态）+ bus 来源 + 挂起 handler。`AgentConfig`（`agent/completion.rs:212`，`pub(crate)`）是 builder、agent、runner **三者共享**的一份配置（#2326）：name、description、bus、model_key、preamble、static_context、additional_params、record_telemetry_content、max_tokens、temperature、tool_choice、max_turns、hooks、output_schema……builder 的每个 setter 改的是它，`build()` 移交 `Agent`，`AgentRunner::from_agent` 整体克隆一份作为**本 run 的私有副本**（per-run 覆写只改副本）。

### sans-IO 状态机：AgentRun

```rust
// File: crates/rig-agent/src/run/mod.rs:445 / :171

pub struct AgentRun { /* max_turns, tool_choice, ... serde 字段，可持久化 */ }

pub enum AgentRunStep {
    CallModel { prompt: Message, history: Vec<Message>, turn: usize },
    CallTools { calls: Vec<PendingToolCall> },
    Done(PromptResponse),
}
```

`AgentRun` 自身**不做 IO、不带 hook**：宿主逐步取 `AgentRunStep`、自己完成 IO、再经 `AgentRun::model_response` / `tool_results` 回填。`AgentRunner` 是给这个机器装上 hook 与 bus 的驱动器（`runner.rs` 顶部注释）。`Agent::resume(run)` 从持久化的 run 继续。

### 三角色 bus

`crates/rig-agent/src/bus/mod.rs`：

| 类型 | 职责 | Send+Sync |
|------|------|-----------|
| `Dispatcher` | 客户端半：dispatch 效果、读 descriptor、绑定 typed view（只持 serde 数据/通道/原子量） | 所有目标恒是 |
| `Registrar` | 实现侧把手：在活的总线上装/换/摘 handler | 与 handler 相同 |
| `BusDriver` | 服务方：持有**唯一** handler 表 | 原生 Send；浏览器 wasm 容忍 !Send |

词汇（`rig_core::effect`）与实现侧契约（`rig_core::serve`：`Serve`、adapters、`ErasedHandler`）都在 rig-core；rig-agent 只是承载运行时。typed view `Handle<F>` 按家族窄化 dispatch（`complete`、`call`、`load`、`top_n`、`embed_texts`…），`Key<F>` 是带家族的 handler key。重放注册入口 `bus::replay::register_all`。

### 工具运行时

- `ToolSet`（`tool/registry.rs:302`）：有序工具集；`RegisteredTool`（`:34`）是一条注册。
- `ToolCatalog`（`tool/catalog.rs:35`）：每轮按 active_tools 过滤出的目录。
- `ToolServer`/`ToolServerHandle`（`tool/server.rs:270/:418`）：检索索引、托管远端工具源（MCP）、每轮快照；rig-rmcp 的客户端 handler 让 `ManagedToolSink` 与 server 工具列表保持同步。
- dispatch 按名解析 → `execute_tool`，结果规范化为 `ToolResultContent`。

## 🧩 rig-ecs 一图速览（详见 07 篇）

- `bus/`：effect 是实体（`PendingEffect` → `InFlight` → `EffectOutcome`，流式走 `Streamed` 组件）；handler 是实体（`Bound` + `HandlerTable` 资源）；driver 是两个系统（`BusSet::{Dispatch,Collect}`）；因果是 `ChildOf` 关系；`BusSet::{Gate,Judge}` 是用户拦截槽。
- `agent/`：运行即图——Agent/Turn/Utterance/Document 都是实体，设置是组件（`Preamble`、`Temperature`、`UsesModel`、`Grant`…）。
- `policy/mod.rs:217` `fold_request` 是**全 crate 唯一**从图到 `CompletionRequest` 的折叠函数（守卫拒绝第二个）。
- `systems/mod.rs`：`RigSet::{Advance,Select,Assemble,Patch,Release,Fold,Judge,Materialise,Checkpoint,Settle}` 十个系统集，嵌在 bus 的 `RigSchedule` 中，host 每 tick 调 `run_to_quiescence`（上限 `QUIESCENCE_CAP = 64` pass）。

## 🧩 总结

- rig-core 的客户端是**值类型 Provider + 能力 Has\* + 泛型 Client**，没有 vtable、没有运行时能力探测——缺能力就是缺 trait。
- rig-agent 的运行栈分三层：sans-IO `AgentRun`（可 serde）→ hook 感知 `AgentRunner`（IO + bus）→ `Agent`/`AgentBuilder`（构造面）。
- bus 三角色把"谁需要服务/谁提供服务/谁真正跑"拆成三个类型，保证 `Dispatcher` 在任何目标上都 `Send+Sync`。
- rig-ecs 用同样的 effect 协议换了一种宿主模型：系统调度代替 future 驱动，组件代替状态机字段。
